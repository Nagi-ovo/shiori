# 高倍缩放：整页位图 vs 视口 tile

阶段 1（`docs/PLAN-RUST-PDF-CORE-2026-09.md`）的实测记录。计时是人工证据，不是 CI
门槛。

## 口径

- 机器：Apple M5 Pro，macOS 26.4.1；Chrome，`bun run dev`（http://localhost:1573/），
  窗口 948×838 CSS px，**dpr 2**。dpr 是本计划的前提：dpr 1 时 letter 页在 8× 也在
  预算内，不需要 tile。
- 文件：`test-artifacts/highlight-cases/` 的 fable.pdf（8 页 letter，612×792 pt）与
  vocabulary.pdf（59 页 A4，595.25×842 pt）。
- 探针：`scripts/perf/zoom-raster-probe.js`（贴进 devtools）。每次从 1× 用
  `setScale` 直接跳到目标倍数，读 `PageCanvas` 的 `rasterStart` / `rasterDone`
  （带位图宽高和 dpr）打点。
  - **清晰耗时**：从改倍数到该倍数最后一次光栅化完成（整页或 tile）。
  - **画布峰值**：每 16 ms 统计全部页面画布的 backing store 字节，取最大值。
- pdf.js 把各页的绘制切片交错执行，单页耗时不能相加，只看清晰耗时。
- fable 7 轮、vocabulary 3 轮，取中位数。另有 3 轮峰值被别的标签的画布污染（切换
  文档时两份文档的画布同时在），已剔除。

## 基线：整页位图（2026-09-25，`fa6a91b7`）

| 文件 | 倍数 | 实际位图（设备 px） | 实际倍数 | 清晰耗时中位数 | 画布峰值 |
|---|---|---|---|---:|---:|
| fable | 2× | 2448×3168 | 2× | 56 ms | 74 MB |
| fable | 4× | 4896×6336 | 4× | 276 ms | 252 MB |
| fable | 8× | 4972×6435 | **4.06×** | 123 ms | 259 MB |
| vocabulary | 2× | 2381×3368 | 2× | 65 ms | 77 MB |
| vocabulary | 4× | 4756×6727 | 4× | 169 ms | 259 MB |
| vocabulary | 8× | 4756×6727 | **4.0×** | 126 ms | 259 MB |

结论：

1. **8× 从来不清晰。** 位图封顶在 32 MP（`MAX_CANVAS_PIXELS`），letter 4.06×、
   A4 4.0×，与代码推算一致。8× 的"清晰耗时"只是那张 4× 位图画完的时间，画完后看到的
   仍是 2 倍拉伸。
2. **高倍缩放的内存是两页挂载 × 双缓冲。** 4× 起单页位图 118–122 MB，两页可见时峰值
   约 250–260 MB，偶发 300 MB（双缓冲交换的瞬间）。
3. **1.5 的门槛**：8× tile 清晰耗时 ≤ 今天 4× 整页，即 fable ≤ 276 ms、
   vocabulary ≤ 169 ms。

## tile（2026-09-25，阶段 1.3–1.5）

实现：超出预算的页面，整页底图降到 8 MP（`TILED_BACKDROP_MAX_PIXELS`），上面铺
512×512 设备像素的 tile，只画滚动容器内可见的部分外加一圈（`TILE_RING = 1`）。预算
内的页面不变（R1）。

口径变化：这次的 Chrome 窗口在 dpr 1 的屏幕上，所以在页面里把
`window.devicePixelRatio` 覆盖为 2。画布像素数、tile 路径和计时与 Retina 相同，只是
屏幕把位图缩小显示。窗口 941×838 CSS px（基线 948×838）。vocabulary 5 轮、fable 3 轮。

| 文件 | 倍数 | 路径 | 实际位图 | 清晰耗时中位数 | 画布峰值 |
|---|---|---|---|---:|---:|
| vocabulary | 4× | tile（A4 在 4× 已超预算） | 底图 2378×3363 + 30 块 tile | 49 ms | 106 MB |
| vocabulary | 8× | tile | 底图 2378×3363 + 30 块 tile，**tile 为真 8×** | 52 ms | 106 MB |
| fable | 4× | 整页（letter 在 4× 仍在预算内） | 4896×6336 | 111 ms | 252 MB |
| fable | 8× | tile | 底图 2486×3217 + 30 块 tile，**tile 为真 8×** | 66 ms | 106 MB |

tile 尺寸（vocabulary，2382×1307 的大窗口，同窗口对比）：

| tile | 8× 清晰耗时 | 画布峰值 |
|---|---:|---:|
| 512 | 71–102 ms | 156–160 MB |
| 1024 | 58–64 ms | 180–196 MB |

结论：

1. **8× 第一次真正清晰**：tile 的位图是 16 设备像素/pt，
   接缝处放大检查无缝。
2. **1.5 的门槛通过**：8× tile 清晰耗时（vocabulary 52 ms、fable 66 ms）低于今天 4×
   整页（169 ms、276 ms）；峰值 106 MB，两页挂载时每页约 53 MB，低于 128 MB/页。
3. **tile 取 512**：1024 快约 10 ms，但峰值多 25%。两者都远在门槛内，取省内存的一边。
4. **R1 的前提不成立**：预算内的整页位图并不比 tile 好。fable 4× 走整页要 111 ms、
   252 MB，走 tile 的 8× 只要 66 ms、106 MB。门槛降到「整页超过底图预算（8 MP，约
   2×）就铺 tile」，3–4× 也能省一半内存、快一倍。代价：快速滚动越过预取的那一圈时，
   会先看到 2× 底图拉伸，约 50 ms 后变清晰；今天 3–4× 在同一页内滚动一直是清晰的。
   这是体验取舍，定案见下节「R1 定案」。
5. 可见区按滚动容器裁剪（不是整个窗口）后，大窗口下 tile 数从 80 降到 70。
6. 没有用 pdf.js 的 `operationsFilter` 跳过块外操作：不裁剪已经远低于门槛，而阶段 3 换
   PDFium 后这条路径就不在了，不值得为它引入未类型化的 `recordedBBoxes`。
7. **批注与表单在 tile 里都显示且只显示一次**：用 pdf-lib 生成的样本（圆、方框、线，
   文本框和勾选框，都由 pdf.js 画在画布上）在 1× 整页与 8× tile 下对照截图，位置一致，
   跨 tile 边界的线条连续，表单在 8× 下清晰。

## R1 定案：门槛降到底图预算（2026-09-25）

tile 改为「整页位图超过 8 MP 底图预算就启用」（Retina letter 页约 2.03× 起）。同样口径
（941×838，dpr 覆盖为 2），fable 各 3 轮：

| 倍数 | 之前 | 之后 |
|---|---|---|
| 2× | 整页 53 ms，74 MB | 不变（7.76 MP，仍是整页） |
| 3× | 整页 | tile 64–66 ms，106 MB |
| 4× | 整页 87–121 ms，252 MB | tile 66–68 ms，106 MB |

快速滚动越过预取圈时，新露出的部分先显示约 2× 的底图，随后变清晰。3× 时底图只拉伸
1.5 倍；而旧做法在 3–4× 下每滚进一页都要整页重画约 100 ms，期间同样显示拉伸的预览，
所以这不是新引入的模糊。
